# rules_osv — design notes

rules_osv wraps a CLI scanner run as tests, so its closest sibling is rules_gitleaks. It takes these conventions from it and from rules_argocd:
- a binary toolchain pinned from published checksums;
- unversioned per-platform repos, where the root module's tag wins;
- tags that can pin versions the package doesn't know (argocd's `sha256` / `cli_sha256`);
- a Python driver with a vendored TOML parser;
- analysis tests;
- maintainer scripts in `tools/`;
- the README / DESIGN / CLAUDE.md set.

What's new is the second pinned input: the vulnerability database, which upstream only publishes at mutable URLs.

## Decisions

| Question | Decision | Why |
|---|---|---|
| How does osv-scanner run offline? | `scan source --offline --local-db-path=<dir>`, with each zip staged at `<dir>/osv-scalibr/<Ecosystem>/all.zip` | That layout is what osv-scalibr's `osvlocal` matcher reads (`enricher/vulnmatch/osvlocal`); `--local-db-path` is hidden in v2.7.1's help but present (env `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY`). `--offline` sets `--offline-vulnerabilities` and `--no-resolve`. `--download-offline-databases` is never passed. |
| How are ecosystems chosen? | By osv-scanner, per package: each package's ecosystem names the directory it loads | A missing directory is an error (exit 127, "could not load db for npm ecosystem"). The driver turns that into "a lockfile has npm packages but `db` has no npm database". So `db` must cover the lockfiles' ecosystems, and only those zips are read. |
| Where do snapshots live? | Assets of this repository's releases, one release per snapshot, tagged `db-YYYY-MM-DD`, named `<Ecosystem>-all.zip` | osv.dev's `<Ecosystem>/all.zip` URLs are rebuilt daily, so a sha256 pin on them breaks within a day. A release asset is immutable once uploaded, free to host, and served from GitHub's CDN. The `db-` tags are separate from code tags (`v0.1.0`), and `--latest=false` keeps them from becoming the "latest release". |
| What is pinned? | `private/db_snapshots.bzl`: per date, per ecosystem, sha256 and size; `DEFAULT_DB_DATE`; generated by `tools/snapshot_db.sh` | One default snapshot. Older dates stay pinned, so `osv.db(date = ...)` keeps working after a refresh. |
| Which ecosystems by default? | crates.io, Go, Maven, npm, NuGet, Packagist, PyPI, RubyGems (306 MB in all; npm alone 221 MB) | They cover the lockfiles most Bazel repositories have. Every ecosystem is its own lazily fetched repository, so the size of an unused one costs a consumer nothing. Others (Pub, Hex, CRAN, ...) can be pinned with `osv.db(sha256 = ...)`. |
| How does a consumer pick ecosystems? | By label: `db = ["@osv_db//:npm"]`. The hub repo `@osv_db` has one `osv_db` target per ecosystem, and each points at its own zip repo `@osv_db_<Ecosystem>` | Loading the hub's BUILD file doesn't fetch anything. Analysing `@osv_db//:Go` fetches only the Go zip. The consumer check asserts the npm zip and other platforms' binaries are never fetched. |
| Custom snapshots and mirrors | `osv.db(date, url = "...{ecosystem}...", sha256 = {eco: sha})`, or an `osv_db` target over any zip or JSON records | The same mechanism serves a newer date, an internal mirror (`file://` works) and extra ecosystems. `osv_db(advisories = ...)` zips records at build time, which the fixture database uses. |
| Is the snapshot date visible? | Every scan prints `OSV database snapshot <date>: <Ecosystem> (sha256 <12 hex>), ...` | The pin is in the hub's `osv_db` (`snapshot`, `sha256`), so the driver doesn't hash a 221 MB file to show it. |
| Local testing before the release exists | `--distdir=<dir of the zips>` | `rctx.download` consults the distdir by URL basename and sha256, so no code path is dev-only. Fixture tests don't need the snapshot at all. |
| Is the test really offline? | `osv_scan_test` is a macro that always adds the `block-network` tag; `//tests:network_blocked_test` shows the tag leaves a test without network | With the linux-sandbox, `block-network` gives the test an empty network namespace. Name resolution may still answer through the host's resolver socket, but every connection fails. Outside a sandbox the tag does nothing, and `--offline` is the guarantee. |
| Ignore file format | osv-scanner's own `osv-scanner.toml`, restricted to `[[IgnoredVulns]]` with `id`, `reason`, `effectiveUntil` (or the deprecated `ignoreUntil`) | It's the format osv-scanner users know, and the ids work unchanged with a plain osv-scanner run. `[[PackageOverrides]]` is refused: it ignores whole packages without per-entry reasons. |
| Who applies ignores? | The driver, not osv-scanner. osv-scanner runs with an empty `--config`, and its JSON groups are filtered the way osv-scanner's `filterPackageVulns` does: a group is ignored if any ID or alias matches an entry | osv-scanner silently stops applying an expired entry, and doesn't report which entries it used. The driver needs both: expired entries fail the test, and unused ones are noted. The empty config also means no `osv-scanner.toml` found next to a lockfile is ever read. |
| Expiry semantics | A date expires at the start of that day, UTC. A datetime without an offset is UTC. Expired entries fail even when the finding is gone | osv-scanner reads a TOML date as midnight local time; UTC keeps a test's result the same on every machine. An expired entry that no longer matches is a stale exception, and still needs review. |
| Malformed ignore files | Every problem is collected and reported together, then the test fails with exit 2 | A missing reason, a missing expiry, a quoted date, unknown keys, duplicate ids or bad TOML. Exit 2 (a broken setup) is kept apart from exit 1 (findings or expired entries). |
| osv-scanner's other implicit behaviours | `--no-call-analysis=all`; `OSV_SCANNER_*` / `OSV_SCALIBR_*` removed; `HOME` set to a temp dir; lockfiles staged as real files under their workspace paths | Go call analysis is on by default and would run the host's `go` (network, toolchain downloads). Staging gives workspace paths in findings for generated lockfiles too. |
| Lockfile names | osv-scanner picks the parser by file name, so `lockfiles` must carry the real names | An unknown name fails with "osv-scanner can't read <path>". |
| `MODULE.bazel.lock` | Not supported: osv-scanner 2.7.1 has no extractor for it, and the tests assert the failure | Checked against the v2.7.1 source (osv-scalibr at `c80efcc25cd9`) and by running it. `bazelmaven` reads `maven.install` from `MODULE.bazel`/`BUILD`, but isn't in the default lockfile extractors, so `MODULE.bazel` fails too. Bazel modules aren't an OSV ecosystem. |
| `go.sum` | Not supported by v2 (`go.mod` is) | Also asserted by a test. |
| Python | Host `python3` 3.8+, `tomllib` else vendored tomli 2.2.1 | The same choice and the same copy as rules_gitleaks. `RULES_OSV_VENDORED_TOML=1` forces the vendored copy, and `//tests:vendored_toml_test` shows it really parses. |
| Binary download | The raw release executables (`osv-scanner_<os>_<arch>`), sha256 from `osv-scanner_SHA256SUMS`, each cross-checked by `tools/update_versions.sh` | Upstream ships executables, not archives. The darwin binaries are pinned but untested here (no macOS host). |
| Version pins | `osv.version(version, sha256 = {platform: sha})`; the root's tag wins over rules_osv's; a platform without a sha fails only when fetched | rules_argocd's pattern. Repos are named per platform, not per version, so `//toolchain` never changes. |

## The fixture database

The scans in `tests/` use six real OSV records (Go, npm, crates.io, PyPI), copied from the 2026-11-16 snapshot and zipped at build time by `osv_db(advisories = ...)`. Tests then:
- take seconds;
- run in CI without the release assets;
- give the same results whatever the snapshot says. The real snapshot reports 17 findings for the "vulnerable" fixtures, not 5, and some "clean" versions have newer advisories.

`//tests:snapshot_test` (manual) runs the vulnerable fixtures against the real snapshot. CI runs it only on `workflow_dispatch` with `snapshot: true`, once the release exists.

## Test caching and expiry

A test result depends on today's date only through ignore expiry, which Bazel can't see. So a cached pass survives an entry expiring. Making `osv_scan_test` uncached by default would rescan on every `bazel test`, which the lockfiles and database, both pinned, don't call for. Instead:
- the output notes entries expiring within 30 days;
- the README suggests running the scan uncached in CI (`--nocache_test_results` or `tags = ["external"]`).

## Not done

- `MODULE.bazel.lock` and `go.sum` (osv-scanner doesn't read them).
- Container image scanning (`scan image`), license scanning (`--licenses`, needs deps.dev) and guided remediation (`fix`): all online or out of scope.
- Transitive resolution for manifests (`pom.xml`, `requirements.txt` without pins): it needs the network.
- A refresh bot: `tools/snapshot_db.sh` and the upload are manual.
